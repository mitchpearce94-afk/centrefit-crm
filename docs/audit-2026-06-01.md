# Centrefit CRM — Full Audit Report

**Date:** 2026-06-01  
**Method:** 12 subsystem reviewers x 5 dimensions (bug / security / data-integrity / pain-point / ux), each finding adversarially verified by an independent skeptic. 74 agents.  
**Result:** 81 confirmed findings.

## Subsystem health

- **quoting** (5 confirmed, 0 refuted): Manual-quote rich-text scope renders raw HTML tags into the customer-facing PDF, and a null-SKU product crashes both product-search flows; several smaller data/UX issues around manual labour and the auto-invoice path.
- **recurring-billing-xero-gocardless** (6 confirmed, 2 refuted): Core GC→Xero recurring chain is well-built (signature verification, idempotency, BR.fulfilled activation, retry cron all correct) but violates two of the project's recurring-billing HARD RULES — contact naming is "Customer — Site" not site-only, and the customer-facing email goes to the contact email not the site billing_email — plus a yearly-RI ingest gap and a double customer-email risk.
- **invoices-reminders-cron** (5 confirmed, 0 refuted): Manual customer-email paths are well-guarded (no auto-send), but the documented overdue-reminder cadence is entirely unimplemented and non-admin reminder sends silently lose their audit trail due to an RLS mismatch.
- **procurement-suppliers-rfq** (9 confirmed, 0 refuted): Core flow (init from quote, split, supplier grouping, draft-PO push) is well structured and DRAFT-first, but procurement pulls in non-parts lines, ships unconfirmed/zero prices to Xero, has a duplicate-PO failure window, and the supplier RFQ send-all has no confirmation guard.
- **nbn-kinetix** (8 confirmed, 1 refuted): Two breaking data-integrity bugs (convert-customer writes non-existent columns; private proof bucket has zero RLS policies blocking staff downloads), plus the known Sales-vs-Communications notification misroute and several status/field inconsistencies.
- **plan-builder** (7 confirmed, 0 refuted): Konva editor and PDF export are feature-rich and largely correct, but the documented "mobile view-only" decision is not implemented (full desktop editor renders on phones), the plan-files storage bucket is fully public (customer security layouts exposed via URL), and several editor operations (crop, rotate) silently break the undo history and device-coordinate integrity.
- **vault** (6 confirmed, 1 refuted): Crypto design is sound (PBKDF2-600k, AES-256-GCM, RSA-OAEP-4096, server only ever sees ciphertext), but the SECURITY DEFINER RPC layer has hardening gaps (mutable search_path, anon-grant), a key-rotation data-loss race, and audit/operational holes that weaken the zero-knowledge guarantees in practice.
- **permissions-auth-rls** (8 confirmed, 0 refuted): Solid session-cookie scaffolding and a genuinely zero-knowledge vault, but admin API routes are protected only by "is logged in" (no role check), the public forgot-password endpoint is an unauthenticated account-lockout vector, and 60 always-true RLS write policies plus broad anon EXECUTE grants weaken the DB floor.
- **scheduler-jobs** (6 confirmed, 0 refuted): Core flows are solid, but the scheduler hides completion-phase jobs from its picker which silently breaks the "Open Job at all statuses" rule, and PP2 invoice auto-creation fires from any authenticated staff with no role gate.
- **assets-sites-customers** (8 confirmed, 2 refuted): Solid CRUD and a correct PIR/duress count, but a hard-rule violation in recurring-invoice Xero contact naming, pervasive site-creation field drift that strands billing emails, missing storage UPDATE policy, and multi-primary-contact ambiguity.
- **notifications-emails-activity** (5 confirmed, 2 refuted): Core fan-out and activity logging are sound, but customer-facing email templates lack HTML escaping (injection), the document_activity RLS is wide-open (read/forge), and staff_notification_preferences RLS contradicts the admin-only-prefs hard rule.
- **settings-products-rules** (8 confirmed, 0 refuted): Functionally rich and well-built UI, but the settings section has no server-side admin gate and several config tables (billing_settings, labour_timings, quote_products, recurring_services) are writable by ANY authenticated staff via RLS; worst of all a GET endpoint can email a Xero invoice to an arbitrary address with no confirmation.

## HIGH (11)

### H1. [quoting] Manual-quote scope-of-works dumps raw HTML tags into the customer-facing PDF
- **File:** `src/lib/quote-pdf.tsx:465 (also 463) and src/lib/quote-engine/scope-of-works.ts:691-701`
- **Problem:** Manual quotes author the scope in a TipTap rich-text editor and store it as HTML (manualScope is HTML, e.g. <p>…</p><strong>…</strong><h3>…</h3>). On the PDF path, manualScopeDocument(scopeText) puts that HTML verbatim into summary.lead, and the PDF renders it as a plain string: <Text style={styles.summaryLead}>{scope.summary.lead}</Text>. React-PDF does NOT parse HTML, so the customer's attached PDF shows literal markup like '<p>ANY AND ALL ELECTRICAL WORKS…</p>' and all paragraph breaks collapse onto one line. The web response page (renderScopeAsHtml, dangerouslySetInnerHTML, white-space:pre-wrap) and the Xero description (renderScopeAsText -> htmlToPlainText) both handle the HTML correctly — only the PDF, which is the document emailed and downloaded by the customer, is broken. This is the reported 'scope-of-works newline/whitespace + rich-text not rendering' pain point, manifesting as worse than missing newlines: visible tag soup.
- **Fix:** For manual quotes, run the HTML lead through the same tokenizer/HTML-to-PDF logic used for system bullets (convert <p>/<br>/<h3>/<li> to Text blocks, <strong> to bold runs) instead of printing the raw string. Reuse htmlToPlainText/tokenize or render manual scope as structured ScopeSystemBlock items so the PDF mirrors the web page.
- *(verifier adjusted critical -> high)*

### H2. [quoting] Null product SKU crashes manual-BOM and BOM-add product search (the toLowerCase crash)
- **File:** `src/app/(dashboard)/quoting/new/quote-wizard.tsx:1015 and 1350`
- **Problem:** Product search filters call p.sku.toLowerCase() and p.name.toLowerCase() with no null guard. The live quote_products table currently has 1 row with sku IS NULL (confirmed via SQL: 363 products, 1 null sku). The Product objects are mapped straight from rawProducts (sku: p.sku) with no coalesce, so as soon as a staffer types 2+ chars into the manual-quote 'Search Products' box (manualBomSearchResults) or the plan-mode '+ Product' inline search (bomAddResults), the filter throws 'Cannot read properties of null (reading toLowerCase)' and the whole wizard step white-screens. This matches the exact reported crash on product search in manual quote.
- **Fix:** Guard every search field: (p.sku ?? '').toLowerCase(), (p.name ?? '').toLowerCase(), (p.supplier ?? '').toLowerCase(). Also coalesce at the products useMemo map (sku: p.sku ?? ''). Optionally add a NOT NULL / default '' constraint on quote_products.sku to prevent recurrence.

### H3. [recurring-billing-xero-gocardless] Yearly RepeatingInvoice children are never ingested or emailed (secondary RI id not matched)
- **File:** `src/app/api/xero/webhook/route.ts:265-279`
- **Problem:** Plans with mixed monthly+yearly cadence create two Xero RepeatingInvoice templates; activate-plan.ts stores the monthly one in xero_repeating_invoice_id (primary) and the yearly one in xero_repeating_invoice_secondary_id. But ingestRecurringChildInvoice matches the owning plan only by `.eq("xero_repeating_invoice_id", latest.repeatingInvoiceID)` and never checks the secondary column. The doc comment on line 263-264 even claims both are checked, but the query does not. Result: every auto-generated YEARLY child invoice finds no plan, logs "no plan owns RI", and is dropped — no local invoices row, no DD notice email, no activity log. The yearly revenue stream is invisible in the CRM.
- **Fix:** Match on either column, e.g. `.or(`xero_repeating_invoice_id.eq.${id},xero_repeating_invoice_secondary_id.eq.${id}`)`, so yearly RI children are ingested too.

### H4. [invoices-reminders-cron] Non-admin reminder sends silently lose their invoice_reminders audit trail (RLS mismatch)
- **File:** `src/app/api/invoices/[id]/send-reminder/route.ts:156-175`
- **Problem:** send-reminder uses the user-scoped server client (createClient()), and invoice_reminders has only two RLS policies: SELECT for any authenticated user, and invoice_reminders_admin_modify (cmd=ALL, qual=is_admin()) governing INSERT. The route has no admin gate, so a non-admin staff member can successfully trigger sendInvoiceReminderEmail() (the email DOES go to the customer — Resend is called server-side regardless of RLS), but the subsequent INSERT into invoice_reminders is blocked by RLS and the route ignores the insert result. Result: a real customer reminder is sent with zero audit record, zero reminder-history row, and reminder_count is still bumped (invoices_update qual=true) — so the count and the history table disagree. The failure-path insert (line 156) also silently no-ops, so failed sends by non-admins vanish too.
- **Fix:** Either gate the route to admins (return 403 if !is_admin), or write the invoice_reminders audit row via a service-role client so the audit is recorded regardless of the caller's role, or add an authenticated-INSERT policy on invoice_reminders. Also check the insert error and surface it rather than ignoring it, so a lost audit row is never silent.

### H5. [nbn-kinetix] convert-customer inserts non-existent first_name/last_name columns and omits required name → contact insert fails, orphaned customer created
- **File:** `src/app/api/nbn-enquiries/[id]/convert-customer/route.ts:61-71`
- **Problem:** The route splits the enquiry name and inserts into customer_contacts using columns `first_name` and `last_name`. The live schema has NO such columns — customer_contacts has a single `name` column that is NOT NULL (verified via information_schema). PostgREST rejects unknown columns, so this insert fails; and even if it didn't, the required `name` column is never supplied. The insert error is never captured or checked (no `error` destructured), so the failure is swallowed. Net result: a customers row and a customer_sites row are created, the enquiry is marked converted, but NO primary contact row exists — an orphaned customer with no contactable person. Every other path (convert-to-recurring line 67-73, recurring-signup line 190-196) correctly uses the single `name` column.
- **Fix:** Insert `name: enquiry.name.trim()` into the single `name` column (matching convert-to-recurring), capture and check the insert error, and fail the whole conversion if the contact insert errors rather than swallowing it. Consider wrapping customer+contact+site creation in an RPC/transaction so a partial failure doesn't leave an orphaned customer.
- *(verifier adjusted critical -> high)*

### H6. [vault] Key rotation can permanently orphan entries created mid-rotation (data loss)
- **File:** `src/lib/vault/api.ts:567-603`
- **Problem:** rotateFolderKey snapshots entries via listEntries(), re-encrypts that snapshot under a NEW folder key, then vault_complete_rotation swaps every member's wrapped_folder_key to the new key. The RPC validates the MEMBER set hasn't drifted but performs NO validation that p_entries covers all live entries. Any entry inserted by another editor between the client's listEntries() call and the swap is left encrypted under the OLD folder key, while all members now only possess the NEW wrapped key. That entry becomes permanently undecryptable — silent, unrecoverable data loss for a password manager.
- **Fix:** In vault_complete_rotation, lock the folder's entry rows (or compare `count(*)` of live entries to jsonb_array_length(p_entries)) and abort with a retry error if they differ, mirroring the existing member-set drift check. Ideally take a row lock on vault_entries for the folder for the duration of the swap.

### H7. [permissions-auth-rls] All /api/admin/* routes gate on authentication only, not admin role
- **File:** `src/app/api/admin/xero/send-test-invoice/route.ts:22-23, src/app/api/admin/recurring/nuke-and-recreate-stuck-plans/route.ts:52-53, src/app/api/admin/recurring/activate-stuck-plans/route.ts:22-23`
- **Problem:** Every admin route except recurring-status/route.ts checks only `if (!user)` and then runs with the service-role client. There is NO `role === 'admin'` check. Any authenticated staff member (including field_staff) can call destructive/financial Xero operations: nuke-and-recreate-stuck-plans (deletes & recreates Xero RepeatingInvoices), activate-stuck-plans (provisions live recurring invoices), patch-ri-includePDF, retry, and send-test-invoice. send-test-invoice is GET + URL-bar triggerable and AUTHORISES + EMAILS a Xero invoice to an arbitrary `?email=` address — a customer-facing Xero send reachable by any non-admin, violating the hard 'never send to a customer via Xero without confirmation/role gate' rule.
- **Fix:** Add an `isCurrentUserAdmin()` (or `assertPermission` with the relevant flag) guard immediately after the `!user` check in every /api/admin route. Better: a shared `requireAdmin()` wrapper applied to the whole /api/admin segment. send-test-invoice should also require explicit POST + confirmation rather than being GET URL-triggerable.
- *(verifier adjusted critical -> high)*

### H8. [permissions-auth-rls] Unauthenticated forgot-password endpoint instantly resets a victim's password (lockout DoS)
- **File:** `src/app/api/auth/forgot-password/route.ts:64-76`
- **Problem:** The public, unauthenticated endpoint immediately calls `admin.auth.updateUserById(existing.id, { password: tempPassword })` and sets must_change_password=true for ANY existing email submitted — no reset token, no email-click confirmation, no rate limiting. Anyone who knows a staff email (e.g. accounts@/sales@ patterns are guessable, and invite/forgot both enumerate via listUsers) can POST repeatedly to permanently invalidate that user's current password and lock them out at will. The email body also falsely tells the user 'your old password still works as long as you don't sign in with the temporary one' — but updateUserById already changed it, so the old password does NOT work. This is both a security lockout vector and a correctness/UX bug.
- **Fix:** Switch to a token-based reset (Supabase generateLink / a signed one-time token emailed to the user) that only changes the password after the user clicks it. Add per-email + per-IP rate limiting. Fix the misleading email copy. At minimum, do not mutate the password until a token round-trip completes.

### H9. [permissions-auth-rls] 60 always-true RLS write policies bypass row-level security on core tables
- **File:** `supabase RLS (live) — customer_sites.sites_insert, plus customers, invoices, quotes, recurring_plans, jobs, suppliers, etc.`
- **Problem:** get_advisors (security) returns 60 rls_policy_always_true warnings across 33 tables including customers, customer_sites, invoices, quotes, recurring_plans, billing_settings, suppliers and parts. These policies have `WITH CHECK (true)` / `USING (true)` for authenticated, so RLS provides effectively no row scoping — any authenticated staff (any role) can INSERT/UPDATE/DELETE any customer, site, invoice or recurring plan directly via the client SDK, regardless of the TS permission flags. The page+data gating in lib/auth is enforced only in app code; the DB floor is wide open, so a crafted client request bypasses all of it.
- **Fix:** Replace `true` write policies with role/permission predicates (mirror has_permission() in the policy, as already done for staff via is_admin()). At minimum gate sensitive writes (invoices, recurring_plans, billing_settings, customers) behind is_admin_or_finance()/has_permission() so the DB enforces what the TS layer claims to.

### H10. [settings-products-rules] send-test-invoice is a GET endpoint that emails a Xero invoice to an attacker-controlled address with no confirmation
- **File:** `src/app/api/admin/xero/send-test-invoice/route.ts:20-101`
- **Problem:** The route is a GET (URL-bar / prefetch triggerable), gated only by `if (!user)` (any authenticated staff, no admin check), and takes a fully attacker-controlled `?email=` query param. It uses the SERVICE-ROLE Xero client to create a real AUTHORISED $1 ACCREC invoice in the production Xero tenant and then calls `emailInvoice`, which sends a Centrefit-branded invoice email to whatever address is supplied. This directly violates the hard rule 'NEVER send anything to a customer via Xero/email without explicit confirmation' — there is no confirmation guard and the recipient is arbitrary. Any logged-in staff member (or a malicious link they click that prefetches the URL) can spray branded invoice emails to any address and pollute the live Xero ledger.
- **Fix:** Convert to POST, require an admin role check (loadPermissionsFor / is_admin), and either hard-pin the recipient to a fixed internal allow-list (e.g. Mitchell's address only) or require an explicit confirm token. Do not allow a free-text recipient on any code path that calls emailInvoice.
- *(verifier adjusted critical -> high)*

### H11. [settings-products-rules] billing_settings is UPDATE-able by any authenticated staff (RLS qual = true)
- **File:** `src/app/(dashboard)/settings/billing/billing-settings.tsx:73-80`
- **Problem:** The billing settings page writes labour cost/sell rates, default markup, GST rate, quote uplift and validity directly from the browser anon-key client. The live RLS policy `billing_settings_update` has qual `true`, so ANY authenticated staff member can change the rates that drive every quote's pricing and margin. There is no server-side admin gate (no settings layout, page is a plain RSC with no role check) and no admin gate at the DB layer. A junior tech could silently halve the labour sell rate or zero the GST rate for all future quotes.
- **Fix:** Change the billing_settings UPDATE/SELECT policies to `is_admin()` (matching xero_connections / categories), and add a server-side admin check to the billing page so non-admins don't even render the editor.

### M1. [recurring-billing-xero-gocardless] Recurring child-invoice email is sent to the customer contact email, not the site billing_email
- **File:** `src/app/api/xero/webhook/route.ts:331-345`
- **Problem:** The HARD RULE states the recurring-invoice recipient must be the SITE email (customer_sites.billing_email), not the customer/contact email. ingestRecurringChildInvoice resolves the recipient as the customer's primary contact email (primary.email) and bails entirely if that is missing — it never reads customer_sites.billing_email (which the plan select on line 271 doesn't even fetch). So the DD-recurring notice email goes to the wrong address, and a site with only a billing_email (no primary contact email) gets no email at all. Note the Xero contact itself IS created with the site billing_email (contacts.ts 126-131), so the app-side notice email and Xero's own send can diverge to different recipients.
- **Fix:** Fetch customer_sites.billing_email in the plan select and send to site.billing_email first, falling back to customer.billing_email, then primary.email. Mirror the same precedence used in findOrCreateContact (contacts.ts 126-130) so the notice email and the Xero contact email always match.
- *(verifier adjusted high -> medium)*

### M2. [recurring-billing-xero-gocardless] Adding a new cadence to an active plan creates a DRAFT RepeatingInvoice that never fires or sends
- **File:** `src/app/api/recurring-plans/[id]/update/route.ts:163-178`
- **Problem:** When a plan edit introduces a cadence that didn't exist before (e.g. an active monthly plan gains its first yearly service), the update route creates a brand-new RepeatingInvoice with the default childStatus DRAFT (comment line 174 says it deliberately never authorises here after the 2026-05-11 incident). But DRAFT RI templates do NOT generate child invoices in Xero — so the new cadence silently never bills. Staff edit the plan, see success, and the new service is never charged. The activate path uses AUTHORISED for exactly this reason; the inconsistency means the same logical action ("this cadence should bill") produces a firing RI from activation but a dead RI from an edit.
- **Fix:** On an already-active plan, newly-created cadence RIs should be created/authorised so they actually fire (AUTHORISED + approvedForSending), or the response must clearly tell staff the new cadence needs manual authorisation in Xero before it will bill. Don't silently produce a non-firing template.

### M3. [recurring-billing-xero-gocardless] GoCardless debug endpoint creates real billing requests against the LIVE account on every call

### M4. [procurement-suppliers-rfq] Draft-PO generation can create duplicate Xero POs when the local status update fails
- **File:** `src/app/api/jobs/[id]/procurement/generate-pos/route.ts:153-189`
- **Problem:** After createXeroPurchaseOrder succeeds, the rows are updated to status='ordered' with the Xero PO id. If that local UPDATE fails (line 165-174), the code throws, which is caught at line 183 and recorded as a 'failure' for that supplier group. But the Xero PO has already been created. The items remain status='order'. Staff see a failure, hit 'Generate Draft POs' again, and a SECOND draft PO is created in Xero for the same items. ### M11. [plan-builder] switchFloor / removeFloor / addFloor flag isDirty even when nothing changed, defeating the unsaved-changes guard

The Xero sync/preview eligibility check uses `p.sku && p.sku.trim() !== ""`, so both are excluded there, but having two different 'empty' representations for the same canonical field is a data-integrity smell that will bite any future query that distinguishes IS NULL from = '' (e.g. unique constraints, dedupe, reporting).
- **Fix:** Normalise to a single empty representation (prefer NULL) in both modes: `sku: sku.trim() || null`.
